# XahauName compatibility decisions

The table describes the original standalone milestone. The second milestone adds ledger-managed suffixes and keyed text and address records. See the [contract reference](contract-functions.md) for current rules and limits.

Reference revision `7968d7fe2e28d1cc4b6b594c44cd538271150b1d`. The XahauName working tree served as a read-only reference. The vectors in `test/wasm.test.mjs` adapt `hook/test/validation.cjs` and `packages/sdk/test/v2.test.cjs`.

| Area | XahauName specification and behavior | XRPName decision and effect |
| --- | --- | --- |
| Canonical names | SPEC and XNIP-0001 define ASCII labels of 1–57 bytes with alphanumeric endpoints and internal hyphens. The Hook folds ASCII uppercase. The SDK's friendly helper removes all whitespace and supplies a default TLD. Its lower-level validator calls JavaScript Unicode lowercase before matching ASCII, which can turn certain Unicode inputs such as Kelvin sign into ASCII. | The contract and SDK fold ASCII case and require the complete `<label>.xrp` name. Whitespace, Unicode, subdomains, and other TLDs are rejected. The inherited reserved labels are `admin`, `root`, `treasury`, `www`, and `xahau`. The API uses the Hook's strict input boundary. |
| Registration | The purchase flow reserves the canonical name before asynchronous mint, offer and claim. Pending and claimed duplicates are separately reported. The Hook also has an administrative registration path. | A successful ContractCall creates the authoritative owner entry directly from transaction `Account`. A single duplicate error covers an existing canonical entry. There is no pending state or purchase price in this PoC. |
| Owner checks | The set-text Hook calls require_owner, which compares the transaction sender with the stored root owner. Other Hook paths use authorize_owner to verify native token identity and ownership. The SDK verified-owner reader also checks the linked objects at a validated ledger. | The owner in contract-controlled storage is the sole name authority at this milestone. A different transaction sender cannot change the description. The SDK needs no token or secondary identity lookup. |
| Text values | XNIP-0002 specifies 1–128 valid UTF-8 bytes for typed text. The generic Hook writer checks length and can store invalid UTF-8 from raw calls. The typed reader rejects it. XahauName supports 15 shared text slots with named keys. | Both contract and SDK enforce valid UTF-8 at write time and keep the byte limit. `description` is the single fixed slot and takes no key argument. Empty writes are rejected. There is no clear operation in this milestone. |
| Failure and atomicity | Hook validation covers malformed transport, duplicates and ownership. The mint/claim flow has staged recovery and weak finalization caveats. | There are two write functions and one data-field write per successful call. Business errors use negative WASM results. Validated failures and repeat ledger reads check that prior state survives. The offline harness also injects a failed host write. |

The next lifecycle milestone should use XNIP-0001, XNIP-0002, XNIP-0004 and the XahauName lifecycle, owner-only burn, and primary tests as the behavioral baseline. In particular, test cleanup of records on transfer and burn, authorization from the current owner, and preservation of a newer primary selection during cleanup of an older name.
